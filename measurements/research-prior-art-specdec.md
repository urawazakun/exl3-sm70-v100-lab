# 先行知見: 投機デコード（ドラフタ/ルックアップ）は「いつ効くか」 — 2026-09-25

目的: 「この実験（DSpark/投機系）は効かないかもしれない」という疑いを、世界の実測で先に判定する。
我々の生データと突き合わせて可否を出す。出典は末尾。

## 結論（先に）

1. **投機デコードの効果は「条件付き」で、条件は文献が明示している**。効く条件は
   (a) **検証コストが隠れる（memory-bound な推論）**、(b) **受理長がコスト閾値を上回る**、
   (c) **投機長を伸ばしすぎない**。**我々の系は (a) が弱い**（EXL3 3bitは命令発行律速＝検証1行の追加コストが高い）。
   → あなたの疑いは**この点で正しい**。
2. **ただし「頭打ち」ではなく、効く条件に寄せられる**根拠もある:
   - **長文脈では訓練なしのルックアップ系が訓練済みドラフタを上回る**（EAGLE3 の受理長 1.28 に対し
     PLD/Suffix Decoding/SAMD/Token Recycling が上、ハイブリッド HOWL は最大 6.14）
     → **我々の n-gram 路線は長文脈でこそ正しい**（我々のオフライン実測もコピー系で平均コミット 8.98）
   - **ドラフタをCPU/RAM常駐にしたほうが速い**というコミュニティ実測がある（RTX PRO 6000 で **DSpark +15〜17%**、
     "drafter faster in system RAM than VRAM"）→ 相談Bの「CPU常駐は無意味」は**反例あり**
   - **無検閲化（abliteration）との不整合は致命的で、直すと大きい**: 無検閲ボディに合わせてEAGLE3ドラフタを
     再調整した実測では**受理率 20.5% → 72.7%（+52pp）＝スループット約2.0×**
3. **我々のデータは文献の予測と一致している**（下の対応表）。特に
   **DFlash2 が MTP に負けた理由は「非無検閲ドラフタ vs 無検閲ターゲットの不整合」で説明できる可能性**が高い。

## 有効条件の式（文献の判定基準を我々に当てる）

「投機長を伸ばして良いか」= **限界受理率 > 相対ドラフトコスト**。我々の実測から直接読むと:
- k=3: 1ラウンド 87.4 ms で 3.04 トークン → 28.8 ms/token（対 46.68）＝**採用** ✓
- k=5/7: 投機を伸ばすと**逆に遅い**（実測）＝限界受理率が既に閾値以下 ✓
- **長文脈では受理率が下がるので、深い投機はさらに不利** → 長文脈では **(a) 投機長を浅く** or **(b) 訓練なしルックアップ** or **(c) ハイブリッド**が文献の推奨

## 我々への含意（行動）

1. **DSpark の A/B は「無駄な実験」ではなく、2つの意味で必要**: ①文献の DSpark>DFlash を我々の系で検証
   ②**「無検閲不整合」仮説の検定**（もし DSpark が MTP を超えなければ、原因は不整合の可能性が高い→再調整という次の手がある）
2. **長文脈では投機を浅くする（またはルックアップに切り替える）**のが文献の推奨。我々は長文脈で
   受理率が落ちることを実測済み＝**k を文脈長で切り替える**価値はある（軽量・コード変更小）
3. **CPU/RAM常駐ドラフタを試す価値は残っている**（コミュニティ実測で +15〜17%、VRAMより速いという報告）。
   #25 の `--spec-draft-ngl 0` 変種がこれに当たる
4. **一番効くのは投機ではなく「長文脈の検証コストそのもの」**: 文献の OWL も EAGLE3 の 0.81× を報告しており、
   我々の 36→18 tok/s の劣化と同根。**jusko の Volta attention カーネル（#24）と fix A/B（#19B）が本命**
5. **投機の話は「ドラフタの質」ではなく「検証の税」で決まる** — 我々の検証税は M=4 で 1.5×（実測）
   ＝**fix B（M=1..8 で検証コスト平坦化）が入ると、木も深い投機も一気に安くなる**（＝順序は fix A/B が先）
